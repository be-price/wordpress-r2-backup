# WordPress専用バックアップと独立復旧の設計仕様

作成日: 2026-10-19（日本時間）

状態: バックアップと独立復旧の設計資料。実装済み機能と利用条件はプラグインREADMEおよび現在のコードを参照してください。OAuth接続サービスは設計目標であり、現在はR2アクセスキーをWordPress内に暗号化保存して直接接続します。

最初の実装単位: 合成データを暗号化して保存し、WordPressなしで検証・復旧できる最小構成。

## 1. 目的と許可された範囲

WordPressの通常操作を専用プラグインへ集約し、Cloudflareに接続してR2へ暗号化バックアップを保存する。WordPress本体、元DB、元サーバーが失われても、同じCloudflareアカウントへ再接続し、別会社のレンタルサーバーへ復旧できることを必須とする。

- 管理者2名が、それぞれ自分の復号鍵で同じバックアップを復号できる。
- 同じバックアップ管理単位の中では、異なるパス・異なる世代でも検証済みの同一ファイル内容を重複保存しない。DBや大容量ファイルのチャンク単位の重複排除までは初期版の必須としない。
- 保存済みオブジェクトの上書き・削除を製品に許可せず、新規追加だけを認める。復旧の読み取り経路と、管理者によるロック設定変更を分ける。
- 正常に確定した世代の全体状態を選択して復旧し、その時点で存在しなかったパスや、別世代の新しい内容を混ぜない。任意の秒まで戻せるPITR（継続記録を使う時点復旧）は保証しない。
- Cloudflareへのログインだけでは復号できない。復号の秘密鍵をWordPress、R2、Gitへ保存しない。
- RPO（失ってよいデータの時間幅）はDB・メディアとも最大1時間、RTO（復旧して再開するまでの目標時間）は翌営業日。
- 最初の保存先はR2のみ。Cloudflare全体の障害・アカウント喪失に備える独立コピーは将来課題として残る。
- 個人情報の保持方針が決まるまで、実データのR2転送・保持設定・削除保護を開始しない。
- 現在の許可は、合成データとローカル隔離環境での設計・実装・検証。実データでの復旧、本番変更、外部デプロイ、権限変更、課金、commit、push、PR作成は含まれない。

## 2. 現在のリポジトリで確認した事実

- `.gitignore`はWordPress本体、`wp-config.php`、`.htaccess`、`wp-content/uploads`、`wp-content/json`、SQLを除外している。Gitからの再構成だけでは保全できない。
- `.gitlab-ci.yml`のDrive同期は`rclone sync`であり、`.rclone-exclude.txt`は`uploads`を除外している。バックアップ世代の保全として流用しない。
- `package.json`の`salvage-db`は取得後にDB取り込みと設定変更を実行する。今回の調査では`npm run salvage`等を実行していない。
- 着手前から`docs/research/`が未追跡で存在する。今回の成果物へ取り込まず、そのまま保全する。
- ローカルのコマンド実行用PHPは8.4.12。`sodium`と`zip`拡張は利用可能。`age`、`restic`、`mysqldump`は現在のPATHでは見つからない。実際のレンタルサーバーの条件は未確認。
- `conductor/workflow.md`は使用しない。既存の取得・取り込み処理、CI、既存プラグインは変更しない。

過去のPHP移行資料、公開経路、メール構成は、現在の動作を保証する証拠として扱わない。

## 3. 方式の比較と推奨

| 方式 | 利点 | 今回の制約との関係 |
| --- | --- | --- |
| 専用プラグイン＋既存の公開鍵暗号ツール＋独立CLI（WordPressを読み込まず動くコマンド） | 2名の復号鍵を分離できる。元サイト外で復旧できる。暗号処理を自作しない | サーバーで外部コマンドを実行できることが採用条件。第一候補 |
| 専用プラグイン＋PHPだけの独立インストーラー | SSHが使えない復旧先でも導入しやすい | 保守された暗号ライブラリで2名分の復号を満たす方式、HTTP経由の秘密鍵入力、実行制限と公開防止の検証が必要。第一版へ同時実装しない |
| Duplicator等の既存製品を中心に運用 | R2保存や独立インストーラーの実績がある | 公式R2接続案内はS3用資格情報を使用する。今回のOAuth接続、秘密鍵の非配置、2名の独立復号を満たす証拠がないため、そのまま採用とはしない |

推奨は第一案。暗号化には`age`の標準形式とX25519公開鍵を使用する候補とする。独自の暗号アルゴリズムや、独自の鍵包み方式は作らない。`restic`の通常の対称鍵構成を、送信元へ復号能力を置かない要件へ無検証で当てはめない。

採用を確定する条件は、公式配布物の固定版とハッシュの確認、対象OSでの実行、2名の独立復号、途中破損の拒否、大容量時のメモリー・一時領域の実測である。サーバーの外部コマンド実行が禁止されていた場合、制限を迂回せず、この方式を不採用としてPHP方式の再設計を提示する。

## 4. 責務と信頼する範囲

| 構成 | 責務 | 保存しないもの |
| --- | --- | --- |
| WordPressプラグイン | 管理者の操作、対象確認、公開鍵設定、取得処理の起動、進行・失敗の表示 | 復号秘密鍵、R2の長期親資格情報 |
| 共通の取得・形式処理 | ファイルとDBの取得、内容による重複排除、公開鍵での暗号化、完全な世代目録の作成、保存単位の検証 | WordPressの起動を必要とする復旧処理 |
| Cloudflare側の接続サービス | OAuth、利用アカウントの確認、サイトごとの許可、限定された転送許可の発行 | 復号秘密鍵、平文バックアップ |
| R2 | 追記専用の共有暗号文、世代別の暗号化目録、最後に追記する完了記録 | 平文のファイル名・内容ハッシュ、DB名、設定、復号秘密鍵、上書き型のlatest・索引 |
| 送信元の重複排除索引 | 内容ハッシュ・サイズ・公開鍵集合と、不透明な保存ID・検証結果の対応を保管する補助情報 | 復号秘密鍵。世代一覧や復旧に不可欠な唯一の情報にしない |
| 独立復旧CLI | 再接続、一覧・選択、完全性確認、復号、復旧先の検査、段階的な復元 | 元WordPressや元DBへの依存 |
| 元サイト外の復旧キット | 固定版ツール、依存物、ハッシュ、形式仕様、手順、接続先と鍵の案内 | 復号秘密鍵そのものとの一体保管 |

CLIの第一の実行場所は管理者の信頼できる端末とする。秘密鍵はその端末の保護された領域に置き、コマンド引数、環境変数、ログ、WordPressの画面に渡さない。復旧先へは保護された経路で検証済みデータを転送する。別サーバー側に必要なSSH、DBクライアント等の条件を事前確認する。

CLIはバックアップ形式の処理を共有しても、`wp-load.php`、WordPress関数、元サイトの設定ファイルを読み込まない。元のWeb公開ディレクトリを丸ごと削除した合成環境で、この独立性を検証する。

## 5. OAuthから転送までの認証経路

OAuth（アカウントへのアクセスを許可する仕組み）と、S3互換API（R2へデータを転送する接続方式）の資格情報を分ける。

1. 固定されたCloudflare側サービスでOAuthの認可コードを受け取る。元WordPressのURLを唯一の戻り先にしない。
2. `state`による要求の対応確認とPKCE（認可コードの横取り対策）を使う。戻り先、要求元、期限を照合し、任意URLへの転送を許可しない。
3. 取得した権限と対象アカウントへの所属・操作資格を確認する。ブラウザーの入力値やメールアドレスだけでアカウントを紐付けない。
4. 保存先のアカウント、バケット、管轄、サイトごとの保存領域を固定する。OAuthの成功をR2への書き込み成功と扱わない。
5. Cloudflare側サービスのR2接続を別途用意する。専用アカウント用のWorkersバインディング（設定済みR2への接続）と、転送許可発行用のR2資格情報を候補とする。これらはデプロイ時の別契約であり、OAuthによって自動作成されたことにしない。
6. 長期のR2親資格情報はCloudflare側の秘密情報保管領域に限定する。送信元には、新規専用キー・作成のみの条件・期限・操作を限定した転送許可を渡す。署名付きPUTだけでは上書きを防げないため、条件を署名にも固定し、保存側のロックと組み合わせる。通常の送信元には削除・上書き・ロック設定変更の許可を与えない。
7. 復旧時は同じCloudflareアカウントで再認証し、選択したバックアップの読み取りだけを許可する。CLIへの引き渡し情報は短期・一回限り・対象限定とし、コマンド履歴へ残さない。元サイトの接続情報がなくても開始できる。
8. 切断、失効、権限不足、アカウント不一致は明示的に失敗させる。送信元用の継続許可も独立して失効できるようにする。OAuthのアクセストークンと更新用トークンも秘密情報として保護し、ブラウザーのURL・アクセスログ・WordPressの通常ログへ残さない。

Cloudflare公式の現行案内では、認可コード方式が提供され、公開CLIクライアントにはPKCEの`S256`が必要とされる。Device Authorization方式は提供されない。独自処理をCloudflareの対応済み方式と表示しない。

外部接続試験で確認するものは、実際に利用できる権限名、OAuthでのR2関連API呼び出し、トークン更新・失効、所属変更、復旧時再接続、アカウント間の混同防止である。現時点では実アカウントへの最小動作確認は未実施。成立しない権限を推測で実装しない。

R2の一時資格情報は既存のR2トークンを親として発行される。`object-read-write`やObject Read & Writeを追記専用の権限と呼ばない。署名条件、既存キーに対する拒否、削除の拒否、ロック設定を変更できないことを、それぞれ実証する。読み戻し検証は接続サービス側で行い、復旧用の読み取り資格情報を送信元へ流用しない。

## 6. バックアップ対象と取得時点

対象はWordPress本体、テーマ、プラグイン、mu-plugins、uploads、独自JSON、その他の再生成できないデータ、DBの全テーブル、復旧に必要な設定とする。`wp-config.php`、`.htaccess`も暗号化対象とし、目録へ秘密値を平文で出さない。サイトごとのDBテーブル接頭辞だけで取得対象を絞らない。

取得前に、対象ルート、対象外、外部ディレクトリへのリンク、DBテーブル数と保存方式、必要な空き容量、実行時間制限を確認する。対象外は再生成できる一時データ等の明示されたものに限定し、読めなかったファイルを除外へ自動変更しない。シンボリックリンクを無条件に辿らず、外部に必要な実体があれば取得対象として明示設定する。

整合性は、以下の取得手順で確立する。

1. 通常稼働中にファイルの事前走査・先行取得を行う。
2. 計画済みの書き込み停止を開始し、Web、REST API、管理画面、WP-Cron、外部Cron、直接DB更新等の書き手が止まったことを確認する。WordPressの保守表示だけでは停止の証明にならない。
3. 停止中にファイルの最終差分を取得し、DBの全テーブルを取得する。InnoDBのトランザクション（DB処理の一貫した単位）だけでは非対応テーブルを含む全体の整合性を保証しない。利用できるDBロックと権限は実環境で確認する。
4. 取得した内容がローカルで変更されない状態になった時点で書き込み停止を解除する。R2への転送完了までサイトを止める構成にはしない。
5. 取得中に変更されたファイル、読めない対象、テーブル数の不一致、必要なDBロックの不足、停止できない書き手があれば、その取得を整合した成功世代として公開しない。

DB取得には対象MySQL/MariaDBと互換性のある既存クライアントを優先する。全テーブルに加えて、トリガー等の復旧に必要なDB定義を列挙し、取得権限の不足を検出する。パスワードをコマンド引数へ入れない。復旧時のイベント・定期処理は、確認が済むまで実行しない。

30分ごとの候補運用で必要な停止時間や負荷が許容されない場合、この手順でRPOを満たせるとは報告しない。サーバー側のスナップショット（ある時点の保存状態）やDBの継続記録など、別の取得基盤が必要かを判断する。

## 7. 保存形式、転送、破損検出

形式名は`wordpress-r2-backup`とする。既存世代と旧jobの形式は`1`を維持する。C2以降に作成する固定取得jobは、取得証拠`captureReport`を必須とする形式`2`を使う。新キットは両形式を読み、形式1の取得証拠を不明と表示する。旧キットは形式2を読めない。共有するファイル暗号文、世代別のDB暗号文、世代別の暗号化目録、最後に作る完了記録を分ける。独自暗号や独自の一括展開形式は作らない。

### 7.1 内容によるファイル単位の重複排除

バックアップ管理単位は、対象サイトのバックアップ系列に割り当てる固定の`unitId`である。異なる管理単位や異なる公開鍵集合の間では、重複排除のためにデータを共有しない。同一単位・同一鍵集合の中では、ファイル名や更新日時ではなく、固定した取得内容のSHA-256とバイト数で同一性を照合する。DBは世代ごとの全体取得を続け、DB内部や大容量ファイル内部のチャンク重複排除は初期版へ追加しない。

`age`は同じ内容でも暗号化するたびに異なる暗号文になるため、暗号文ハッシュだけで同一内容を判定しない。送信元の索引はWeb公開外の所有者専用領域に置き、`unitId`・内容SHA-256・サイズ・公開鍵集合IDから、不透明なオブジェクトID、暗号文のサイズとSHA-256、作成・照合の進行状態を引く。公開鍵集合IDは公開鍵を正規化・ソートした集合の識別子であり、内容ハッシュの代用品にはしない。R2キーは`files/<keySetId>/<opaqueId>.age`等とし、ファイル名や平文の内容ハッシュを出さない。

索引は独自の暗号方式ではなく、既存のSHA-256と既存暗号文を対応付ける補助情報である。作成時に同一の変更不能な入力から平文ハッシュと暗号文を生成し、転送後に暗号文を読み戻して照合する。再利用時も、保存先に実体があり、サイズ・暗号文ハッシュ・鍵集合が索引と一致することを接続サービス側で確認する。単なる索引の値や、R2に同じ名前のキーがあることだけでは再利用しない。

同じ単位の取得は排他処理で直列化する。オブジェクトIDの予約を索引へ永続化してから転送し、暗号文候補のハッシュ・サイズも送信前に記録する。再試行は同じ予約IDを使い、既存実体が検証済み候補のいずれかと一致すれば再利用する。一致しない実体を上書きしたり、別IDで保存し直して破損を隠したりしない。段階Aは専用ファイルロック、段階Bは接続サービスの単位別排他と古い実行許可の無効化を使い、複数送信元が独立に保存IDを発行しない。管理単位ごとに稼働中の索引は1つとし、送信元の切り替えには取得停止・索引再構築と現在世代への追従確認を要求する。古い索引の送信元が次の排他枠を得ても取得を再開できないよう、索引の進行位置と送信元の世代を接続サービスで照合する。この管理状態を失った場合も、取得だけを停止して再構築する。

索引が消失し、保存先に既存データがある場合、新規取得は停止する。管理者が信頼できる端末で独立CLIを使い、R2の完了記録・暗号化目録と、現在の鍵集合配下の共有暗号文を読み、復号して内容とハッシュを検証し、索引を再構築する。完了世代から未参照の正常な暗号文も走査し、中断直後の保存実体を無条件に重複作成しない。保持中世代の参照先が壊れていれば再構築を正常完了にせず、未参照の破損実体は報告して再利用しない。送信元へ渡す再構築結果はハッシュ・ID・照合情報だけとし、秘密鍵を渡さない。

再構築中は送信元を停止し、未完了転送の終了・許可失効も待つ。索引の再構築待ちでRPOを満たせない可能性は明示する。世代一覧と独立復旧はこの索引や接続サービスのDBがなくても動く。

### 7.2 新規作成だけを許可する保存

送信元は保存済みキーの上書き・削除・ロック変更を行えない。復旧の読み取り資格情報と管理者の保存設定変更権限は別にする。署名付きPUT URLを発行するだけで、この性質を満たしたとは扱わない。

単体PUTには新規専用キーと`If-None-Match: *`を使い、条件も署名対象にする。公式の現行S3互換仕様には、この条件が確定済み保存状態に対して原子的に評価され、同時作成は最大1件だけ成功する旨が記載されている。既存時の`412`は上書きの許可ではなく、既存実体を照合する契機にする。新規データ、目録、完了記録のいずれにも適用する。

さらに、保護対象の保存領域にBucket Lockを設定し、保存側でも既存オブジェクトの上書き・削除を拒否することを本番運用の条件にする。接続サービスは取得ごとに必要な保存領域のロック適用を確認し、不在や保護不足なら転送許可を発行しない。製品へロック設定の変更権限を与えない。Cloudflare管理者はルールを解除できるため、管理者自身やアカウント全体の侵害に対する変更不能性を保証しない。設定は保持方針と外部変更の明示承認後にだけ行う。

大容量ファイルはストリーム処理で暗号化し、分割転送を使う。初期の転送単位は64MiBを候補として実測する。分割転送の完了処理に単体PUTと同じ条件を使えるとは仮定しない。予約された新規キー、接続サービスが管理する完了処理、保存側ロックを組み合わせ、同時完了・応答喪失後の再試行でも既存実体が変わらないことを段階Bで実証する。実証できなければ、この転送方式を本番で有効にせず、条件付きPUTが可能な分割保存方式を再設計する。

段階Aのローカル模擬保存先も、新規作成専用とする。完全に書けた一時ファイルを、既存先を置き換えない原子的な操作で公開する。通常のrenameによる既存先の置換は禁止する。既存キーへの作成・上書き・削除はAPIで拒否し、復旧読み取りは別の役割を使う。この模擬契約は、同じOS利用者による直接のファイル削除まで防ぐものではなく、実R2の権限やBucket Lockの実証とは分ける。

### 7.3 全体構成を持つ世代と完了順序

- 各世代にはランダムな世代IDと、その取得時点の全パス・空ディレクトリ・DBの状態を持つ目録を作る。過去世代への差分指示だけにはしない。同じファイル暗号文は複数パス・複数世代から参照できる。
- 目録には、`unitId`、取得時点、整合性結果、相対パス、種別、サイズ、平文SHA-256、共有暗号文ID・SHA-256、公開鍵集合、DB暗号文と互換情報を記録し、2名の公開鍵へ暗号化する。完了記録に平文のファイル名・内容ハッシュを含めない。
- 新規共有暗号文・DB暗号文の追加と読み戻し確認、再利用先の照合、暗号化目録の追加と読み戻し確認を済ませ、最後に`commits/<snapshotId>.json`を新規追加する。目録は`manifests/<snapshotId>.age`とする。世代をまたいで上書きする`latest`やR2索引は置かない。
- 一覧はR2の完了記録を列挙して作り、接続サービスのDBだけに依存しない。完了記録がない世代は選択できない。選択後は目録と全参照先を検証し、完了記録だけで破損がないと表示しない。
- 復旧するのは選択した目録の全体構成だけである。共有実体の一覧や新しい目録と合成しない。その時点で削除済みのパスを復活させず、別世代のファイルやDBを混ぜない。
- 欠落、切り詰め、ハッシュ不一致、未知の形式、鍵集合不一致は復旧先の公開前に拒否する。ETagを分割転送全体のハッシュとみなさない。
- 再開できるのは、保持した変更不能な暗号文の転送と検証済みダウンロードである。暗号化や取得を途中バイトから無条件に再開しない。

### 7.4 共有実体の保護と削除主体

共有実体を作成日基準で一律期限削除すると、新しい保持中世代の参照先を失う。そのため、初期版にはオブジェクトの期限削除・世代削除・参照切れデータの自動削除を設けず、製品の削除操作も拒否する。未完了転送の中止や、保存領域外のジョブ専用一時ファイルの後始末とは分ける。

ロック期間が後から作られた参照世代より先に切れないよう、初期運用の候補は管理単位の保護領域に対する無期限ロックとし、有限期間の作成日起算ロックを無検証で採用しない。ただし、個人情報を無期限保持してよいという決定ではない。保持方針がこの候補と両立しない場合は、参照中の保護延長や保存単位の構成を別途決めるまで実データ運用を開始しない。

将来の削除主体は通常のプラグインとは別の保存管理者とする。初期版の管理単位を廃止して削除するには、新規取得停止、保持対象世代が残っていないこと、暗号化目録を解読した参照確認、復旧中の利用がないこと、個別の明示承認が必要である。保護領域に保持中の参照が1つでもあれば、その領域のロックを解除して削除しない。読めない目録・不明な形式・未解決の転送があれば削除を止める。参照切れの一部実体だけを消す自動処理は今回実装しない。

一時領域はWeb公開外、所有者だけがアクセスできる場所とし、平文を最小期間だけ置く。通常の削除をSSD等での完全消去と説明しない。

`age`の認証付き暗号とハッシュは破損を検出するが、公開鍵を知る攻撃者による世代全体の偽造を、それだけで防げるとは主張しない。取得元とCloudflareの接続サービスを信頼する設計である。Cloudflareアカウント全体の侵害・喪失に対する独立した真正性証明やコピーは、現在のR2限定構成では保証しない。

## 8. 2名の鍵と復旧キット

鍵は管理者それぞれの端末で作成し、プラグインには公開鍵だけを登録する。開始前に合成データの確認用ファイルを両名が各自の秘密鍵で復号し、鍵の登録間違いを検出する。片方しか確認できていなければ運用開始しない。

公開鍵を変更した場合、旧公開鍵向けのデータをそのまま新世代へ再利用しない。現在の取得元から新しい鍵一式で取得し直す。旧世代の復号には旧秘密鍵が必要であり、鍵の変更で過去のアクセス権が消えるとは説明しない。鍵を2つとも失うと復旧できない。

元サイト外に、復旧CLI、固定版依存物、公式配布物の検証情報、形式仕様、実行手順、Cloudflareアカウントと保存先の案内、OAuthクライアントを再設定する手順、各管理者の鍵の所在案内を保全する。R2にだけ置かず、信頼できる管理端末等にも保管する。キットと秘密鍵は保管を分ける。

## 9. 独立復旧の手順と安全条件

1. 復旧キットのハッシュと実行環境を確認し、WordPressを読み込まずCLIを起動する。
2. Cloudflareへ再接続し、アカウントと保存先の一致を確認する。正常完了した世代だけを一覧にする。元サイトや元DBへ照会しない。
3. 管理者の秘密鍵で目録を復号し、対象、取得時点、DB・メディアの時点、必要容量と互換性を表示する。未知の形式・鍵不一致・欠落はこの段階で停止する。
4. 復旧先の所有権を、SSH接続と指定ディレクトリへの確認用ファイル作成・読み戻し、およびDB接続先・権限の確認で検証する。任意ホストや任意パスへ転送するための公開APIにしない。
5. PHP、必要拡張、DBバージョン・照合順序、ファイル権限、ディスク容量、URL、パス、Webサーバー設定を確認する。条件不足は上書き前に止める。
6. 新しい空の復旧用ディレクトリと専用DBへ取得する。絶対パス、`..`、重複・正規化後の衝突、リンク経由の逸脱、特殊ファイルを拒否し、件数・サイズの上限も確認する。既存公開先へ直接展開しない。
7. 暗号文と復号後のハッシュ、サイズ、全テーブル、必要ファイルを照合する。検証済みの単位だけを進行記録へ残し、失敗は表示して再開点を示す。途中のDB取り込みを無条件に再実行せず、隔離DBの作り直しまたは確認済み境界から再開する。
8. 新しいDB接続情報で設定を作成する。古い認証情報を自動で再利用しない。URL変更はWordPressのシリアライズ済みデータ（文字列長等も持つ保存形式）を理解する既存手段で行い、単純なSQL文字列置換をしない。
9. 対象パス・DB・上書き内容を提示して、操作者の明示確認を得る。復旧先の書き込みと定期処理を止め、既存状態を退避してから切り替える。ファイルとDBを一括で原子的に切り替えられるとは仮定しない。
10. 確認用URLで動作を確認し、書き込み再開、Cron、外部連携の再接続を個別に行う。切り替え失敗時は停止を維持し、退避したファイルとDBへ戻す。復旧用の入口、短期資格情報、一時平文を後始末する。

今回この手順を実行するのはローカルの合成データだけ。本番・実データに対する復旧や切り替えを行わない。

## 10. RPO・RTOと運用上の受入条件

30分ごとの候補取得は、WordPressへのアクセス発生に依存するWP-Cronだけで動かさない。外部の確実な起動経路を別途設定するが、その外部設定は現在の許可外である。同時実行を防ぎ、前の処理が終わらない場合も成功扱いで飛ばさない。

最新の復旧可能世代が含むDB時点とメディア時点の、古い方からの経過を継続測定する。1時間を超えたら目標未達とする。各時点から整合性確認・転送・読み戻し・完了までの遅延も含める。取得周期、処理時間、失敗後の回復時間の実測なしに達成を報告しない。

測定項目はデータ量・ファイル数、初回と変更取得の時間、DB取得時間、書き込み停止時間、CPU・メモリー・I/O負荷、一時領域、転送・再試行時間、復号・復元時間、操作者が行う準備時間である。小さな合成データの成功だけでは本番規模の目標達成を認定しない。

## 11. WordPressプラグインでは保全できないもの

公開サイト全体の復旧には、中継VPSのNginx設定、DNS、TLS、メール、静的サイト、外部サービス、アカウント・権限・課金の情報も必要になる。これらをWordPressのバックアップ済みと表示しない。

実環境を読み取りで再確認したうえで、各サービスからの設定取得・復旧手順を別に作る。メール本文や個人情報の取得には別の保持方針を適用する。今回の実装で中継サーバー、DNS、メール、外部アカウントを変更しない。

## 12. 段階的な実装と検証

### A. 最初の縦断実装：合成データによる独立復旧

- 配置候補は`wp-content/plugins/wordpress-r2-backup/`、元サイト外へ配布できるCLIは`tools/wordpress-r2-recovery/`。共通の形式処理はプラグインのWordPress非依存部分とし、復旧キットにも同梱する。
- 専用プラグインは機能が準備中であることを表示し、実データ取得・外部転送を初期状態で拒否する。自動起動や現在のサイトへのバックアップ操作を追加しない。
- 固定版`age`、2名の合成鍵、合成WordPress構成、専用の使い捨てMySQL/MariaDBに作った合成DBを使う。実サイトのファイル・設定・DBは読み取らず、既存のLocal環境のDBも使わない。独立したDB環境を用意できない場合は、その検証を未実施と明示して段階Aを完了扱いしない。
- 暗号化目録とデータを、R2の代わりに明示指定したローカル保存先へ書く。ローカル方式はテスト用として固定し、R2障害時の自動代替先にしない。
- 同一内容を別名・別世代で取得しても共有ファイル実体数が増えず、変更した内容だけが新規実体になることを確認する。同時取得と再試行も同じ単位の排他・予約を使う。
- 保存先の新規作成専用契約を検証し、既存キーの上書き・削除を拒否する。古い共有実体への模擬期限削除も拒否され、保持中の新世代を復旧できることを確認する。
- 元ディレクトリ、元DB、送信元の索引を破棄した合成環境で、独立CLIだけを使い、選択した世代を別の空領域へ復旧する。削除済みパスや新しい世代の内容を混ぜない。
- 管理者が片方の秘密鍵で索引を再構築し、送信元へ秘密鍵を渡さず共有実体を再利用できることも確認する。現在の鍵集合と異なる既存実体を再利用しない。
- 両名の独立復号、誤鍵の拒否、共有実体の破損・欠落・未完了の拒否、パス逸脱の拒否、許可していない上書きの拒否、中断後の再開を確認する。

受入条件: WordPress本体、元DB、送信元索引が存在しない環境で、両名が別々に選択世代の全体状態へ復旧できる。ファイル内容・パスの存在と削除・件数・ハッシュ、DBの全テーブルと値が一致する。共有、鍵変更、同時処理、追記専用保存、参照保護の追加ケースが通り、異常系で既存の復旧先を変更しない。これは実R2のロック、本番対応の完成、任意の秒への復旧、RPO/RTO達成を意味しない。

### B. Cloudflare接続とR2転送

ローカルのCloudflare模擬環境で接続サービス、資格情報の分離、分割転送・期限切れ・失効を検証する。実アカウントでのクライアント作成、Workers配備、R2有効化・資格情報作成、合成データ転送は、必要権限・費用を提示して別途明示許可を得てから行う。

受入条件: 認証できても別アカウント・別バケットへ書けない。送信元は既存キーの上書き・削除・保存設定変更ができない。単体PUTの競合、署名条件を外した要求、分割転送の同時完了・再試行、ロック中の上書き・削除を実R2で確認する。失効・期限切れ・拒否・通信中断を検出し、不完全世代を正常表示しない。元サイトや索引がなくても再認証して合成バックアップを選択できる。

### C. 実際の取得処理と実行条件

対象ホストのPHP・実行権限・DBクライアント・空き容量・停止可能な書き手を確認する。合成DBの全テーブル取得、処理中変更、大容量、差分、障害後の再取得を検証し、通常の操作画面へ接続する。実サイトへの導入・有効化は別途扱う。

受入条件: 対象漏れや整合性不足を成功扱いしない。初回・変更時の実測値から、30分候補の成立条件と必要な停止時間を提示できる。対象環境で動作しなければ、ローカルでの成功と分けて未対応とする。

### D. 運用開始の条件

個人情報の保持期間・対象・削除権限・鍵喪失時対応を決定する。R2の保持・削除保護は対象と費用を提示し、承認後に設定する。共有実体の保護が保持中世代より先に切れないことを確認し、作成日だけを基準とする期限削除を有効にしない。Bucket Lockを管理者も解除不能な保全やCloudflare全体への耐障害性と同一視しない。

受入条件: 元サイト外の復旧キットと2名の鍵の保管を確認できる。合成環境で中断を含む復旧を完走し、翌営業日までの目標を評価できる。実データ保存開始には別の明示許可がある。実データの復旧は今回の許可には含めない。
